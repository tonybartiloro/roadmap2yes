## Risposte (author, T1/T2)
- REV-101: fixed (atomic upsert that takes the row lock; same as REV-1).
- REV-102: fixed. `private.rsvp_limits()` is the single source (10 / 20 / 15 min / 15 min); `rsvp_hit_ip` and `rsvp_hit_link` use it and the cleanup age is `greatest(window, lock)`; pgTAP checks the values and that a 10-minute row is kept and a 20-minute one dropped.
- REV-103: fixed: `shared_by` is forced to the caller (null if nothing was shared), a future `shared_at` is refused with `invalid_previous`; tested.
- REV-104: accepted as a residual, no change (own wedding only; derivation is an app invariant, to be written in `sicurezza.md`).
- REV-105: note for S2/S3: always list columns on `rsvp_links`, never `select('*')`.
- REV-106: accepted (fixed window, same shape as login); S2 treats "no IP" as exceptional.

## Verified, no finding (security checklist)
- **SECURITY DEFINER**: every function pins `search_path = pg_catalog, pg_temp`; objects are schema-qualified (`extensions.digest`, `auth.uid`); no dynamic SQL anywhere. All `EXECUTE` is revoked from `public, anon, authenticated` (default privileges of `public` also deny them); the 3 public RPCs go to `service_role` only, the 6 couple RPCs to `authenticated` only. Proved by pgTAP (`rsvp_public`, `rsvp_rls`, `core_schema` allowlists, `qa_catalog_matrix`). `private` helpers are not executable by API roles; `private` is not an exposed schema (`config.toml schemas = ["public"]`).
- **Couple RPCs**: each starts with `auth.uid()` not null, wedding from `private.current_wedding_id()` (never a parameter), `guests/write` (`read` for `rsvp_status`). Only `partner` has `guests` rows, so family/planner are denied (tested incl. a planner given `read` only). Other wedding: group/guest/link lookups filter on the caller's wedding; "not yours" and "does not exist" give the same `link_not_found` (no oracle). `undo_guest_import` keeps the `guests/delete` check; the change only adds protected people and a `skipped` count.
- **RLS and grants**: `authenticated` has SELECT only on the 3 tables (tested: no non-SELECT grant, no anon grant); `token_hash` is absent from the column grant (`qa_catalog_matrix` sel_hidden); `guest_groups` gets only `update (rsvp_mode)`, written under the existing `guests/write` policy. Limiter table: RLS on, no policy, all grants revoked, never audited.
- **`rsvp_page` key set**: closed (`ok, couple, date, location, theme_id, people`; person: `id, first_name, last_name, category, status, diet, diet_note, answered_at`), asserted exactly in pgTAP, plus a regex proving no contact/note/side/table/group/other-guest text. Link coverage is computed by one function (`rsvp_cover`) with the wedding taken from the link row, so no cross-wedding leak; the same names in another wedding are not mixed (tested).
- **No oracle**: unknown, null, wrong-length, revoked, replaced, expired, dormant, deleted-target and empty-group links all reach the same branch (`rsvp_resolve` finds nothing) and return `{ok:false}` with the same side effect (one IP hit, none if the IP key is null). `rsvp_gate` writes nothing and reveals the theme only for a working link. Differences left: timing of the working path vs the failing path (the status already tells them apart, so no new information) and `invalid_answers`/`blocked` appear only on a working token. Neutral answer on submit with a bad payload on a dead link: tested.
- **Limiter**: row lock under `for update`; count reaches `p_max` then locks (the 10th/20th hit is allowed, the next refused); a locked key is not extended; window/lock expiry resets; cleanup keeps locked rows (`skip locked`); null IP means no counter; working tokens never touch the IP counter, so a shared IP cannot lock out valid guests; the per-link key is `sha256(link id)` and is only reachable with a working token, so a stranger cannot lock a link; varying the token only changes the hash, the IP key is what is counted (an attacker cannot rotate it). Dead-link submits feed the IP limit (tested). Own table, not the login one (tested).
- **`rsvp_submit`**: the whole payload is validated (`rsvp_item_ok`, every cast failure is "not ok") before the per-link hit and before any write; bad payload on a working link raises `invalid_answers` (not counted, no write, all or nothing, tested for 20 cases incl. 101 items); ids are intersected with the link's CURRENT people; the hit is taken before the writes and its row lock serialises submits per link; a person is covered by one link only, so no two locks cover the same row. Identical rewrite is skipped by the trigger (no version, audit or `answered_at` change). `source` is `guest` for the secret key. Text with `<script>` is stored as data (rendering is S2).
- **Audit / purge**: `audit_row('status','diet','diet_note')` on answers and `('token_hash')` on links (asserted in pgTAP over real public-RPC writes; the skipped identical update fires no audit trigger). `rsvp_responses`, `rsvp_links`, `rsvp_link_people` cascade from the person/group (composite FKs `on delete cascade`), so "Elimina definitivamente" and the `rsvp_mode`/restore cases delete answers, links and snapshots; `rsvp_lifecycle` covers it.
- **Seed**: only fake names and a fake secret/token, idempotent, in `supabase/seeds`, which `migrate.yml` never runs (`--include-seed` forbidden, no `db reset --linked`).

## Forward notes for S2 (not findings on this diff)
- Wrapper: never log or forward the raw RPC error object (`details` of a check violation can echo the row, including `diet`); map `invalid_answers`/`invalid_key` to a generic message; call the RPCs with POST (not `get: true`) so hashes stay out of URLs.
- Proxy: a token of a malformed shape should still reach the same neutral path (and count on the IP) or be rejected without side effects; it must not answer differently from an unknown token.
- Refuse `RSVP_LINK_SECRET` equal to the documented local fake value in production/preview.
- The R-07/export features that will write `diet_note` into CSV must neutralise leading `= + - @`.
- QA-9 concurrency is covered only sequentially in pgTAP; a real parallel test (two connections) belongs to S2/e2e as planned.
