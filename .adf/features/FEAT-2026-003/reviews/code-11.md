# Code review 11 - T12 import migration, security round (commit 5ec1f7d)

Verdict: **approved with one should-fix** (0 blocking, 1 should, 3 nit). Bar: same as code-2 (L feature). Checked `20261202200000_guests_import.sql`, `guests_import.test.sql`, allowlist and oracle edits. pgTAP not run.

## Verified OK
- `search_path`: `pg_catalog, pg_temp` on both RPCs and on the two helpers; every table and function reference is schema-qualified (`public.`, `private.`, `auth.`).
- Grants: `revoke all ... from public, anon, authenticated` on all four functions, then `grant execute` to `authenticated` for the two RPCs only; the private helpers stay unreachable. Allowlist (`core_schema.test.sql`), `qa_catalog_matrix.test.sql` and `matrix.ts` list exactly the two new names as `user`; anon denial is tested.
- Authorization: the wedding is `private.current_wedding_id()` (caller's membership), never a parameter; the permission check is the FIRST statement (`guests/write` for import, `guests/delete` for undo), before the payload is looked at. `auth.uid()` null (secret key / service role) is refused; family and a user with no membership are refused (tested, `forbidden`, 42501).
- Cross-wedding: undo filters `wedding_id = v_wedding AND import_batch_id = p_batch_id` on people and groups; a batch of another wedding or an unknown/null id changes nothing (tested with a second founder; the batch is verified intact). Imported groups carry the caller's `wedding_id`; reuse only matches live groups of that wedding.
- Undo scope: groups are deleted only if tagged with that batch (so a reused, pre-existing group is never touched) and only when no guest, live or soft-deleted, still points at them (tested: the group someone filled meanwhile stays). Physical delete is the ONE intended exception to "nothing purges" and the oracle was narrowed by name only (`guests_model.test.sql`).
- Abuse bounds: 500 rows and `octet_length(p_rows::text) > 960000` are checked after the permission and before any row is read; the client's 900 KB (921600 B) leaves about 38 KB of margin for the spaces `jsonb::text` adds (about 17 B x 500 rows). Per-field limits come from the table CHECKs; a group name over 80, bad phone/side/category, null name all end in `invalid_row`.
- Atomicity: the inner `begin ... exception` block is a sub-transaction, so groups created before a bad row are rolled back (tested: "Gruppo fantasma" is not left behind).
- Audit: the guests/groups triggers use the deny-list (`audit_row(...)`); the new test counts more than 500 audit rows (not vacuous) and finds no personal key and no personal value after import, undo and hard deletes.
- Error messages: check/not-null/type/truncation failures are replaced by the fixed `invalid_row` (so the "Failing row contains (...)" DETAIL never leaves); other codes are fixed words (`forbidden`, `too_many_rows`, `payload_too_large`). The server action maps all of it to fixed texts anyway.
- Group key (REV-40): `private.guest_group_key` = collapse the explicit whitespace set to one space, trim the same set, `lower()`; set equals ECMAScript WhiteSpace + LineTerminator (no U+0085, correct). Same order as the TS `groupKey`. Live groups only, one group per key per batch, oldest group wins (`order by created_at, id`). Tested with NBSP, tab, U+3000, thin space, `È`/`è`, deleted group of the same name, and accents NOT ignored. The `lower()` residual is acceptable: it can only create a group instead of reusing one (the preview may then say "esistente" and the import creates a new one: cosmetic, not a wrong merge).
- Types: `database.types.ts` has `import_guests(p_rows)` and `undo_guest_import(p_batch_id)`, matching `import-actions.ts` (`UNDO_ARG`); the loose cast can be dropped.

## Findings
**REV-53 (should)** `undo_guest_import` (`:159-165`): the physical delete has no age or "untouched" bound. Any member with `guests/delete` can remove EVERY person of a batch at any time (the batch id is readable: `grant select` covers `import_batch_id`), including people the partners have since edited, seated at a table or given a phone number, and unlike "Elimina" there is no "Eliminati di recente". Fix, pick one and record it in the plan P4: (a) only delete people still unchanged since the import (`version = 1`) and return how many were kept, and have the UI say it; or (b) refuse after a short window (for example 24 h from the batch's first `created_at`) with a fixed code; or (c) accept as is and document it as a decision in `design.md` with the user's consent. The toast flow only offers undo for 8 s, so the realistic risk is a stale or replayed id.

**REV-54 (nit)** `guest_trim_ws` / `guest_group_key`: the whitespace set is spelled with literal invisible characters inside the regex; an editor or copy/paste normalisation could silently change it, and the test only exercises NBSP, TAB, U+3000, U+2009. Fix: write it with `E' ...'` escapes or generate the class from `chr()`, and add one test that loops over every code point of the set (including VT, FF, U+1680, U+2028/2029, U+202F, U+205F, U+FEFF) and compares with an expected key.

**REV-55 (nit)** `:127-129`: the handler lists four SQLSTATEs; an unlisted data error (for example `program_limit_exceeded`) would reach the caller with Postgres' own message. The action never returns it, but the RPC is callable directly: use `when data_exception or integrity_constraint_violation` so every row-level failure collapses to `invalid_row`.

**REV-56 (nit)** `guests_import.test.sql`: add (a) undo of a batch whose people were edited or soft-deleted since (documents REV-53's choice), (b) a retry case if REV-47 gets a client batch id (the RPC still generates its own `gen_random_uuid()`; the double-import on a lost response is open until then), (c) the per-field CHECK for `notes` over its limit through the RPC.

Open from other reviews: REV-47 (idempotent retry) needs the RPC to accept an optional client batch id (unique per wedding) and return the first result on repeat; not blocking T12.
