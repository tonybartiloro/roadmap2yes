## Developer-declared deviations
1. One neutral message for every unusable link: accepted. Matches `invitation_by_token`; tested (unknown, wrong shape, expired, revoked, used).
2. Masked email and inviter name on the page: accepted for a token holder (the masked form shows the first character and the domain only). See REV-7 for the read path.
3. `createUser` retried once on GoTrue's 500: accepted. The retry restarts from step 1, so the DB decides again (a racing account of another wedding gives `email_in_use`). Side effect: a second `send_count` and a second `partner_account_created` event on a race. Harmless.
4. Null event target for a brand-new address: accepted. The bind step does not rewrite it; fine for Novità.
5. No test for "compensation step 1 also fails": the second test in the "change B's pending email" block (simulated crash after step 1) already proves the repeat converges, so I treat this as covered. REV-1 is the real gap in this area.
6. Token steps with the service key: accepted and required (`invitation_by_token` is not executable by `authenticated`).

## Security summary
Verified and sound:
- Order DB then admin: every admin call in `admin-ops.ts` follows a DB step that authorised it and uses only the returned id (`target_user_id`, `invitee_user_id`, `delete_user_id`, `user_id` from `invitation_by_token`). No client id or email reaches the admin API; `changeOwnCode`/`changeOwnEmail` also check `target === selfId`. Tests assert the admin API is NOT called when the DB refuses (joined B, accepted revoke, no target).
- Revoke deletes only `delete_user_id`, which the DB returns only while `account_reusable`; `user_not_found` is tolerated, so repeat converges.
- Takeover: non-reusable accounts get `email_in_use` in the DB (test with a hash chosen by the caller); temp code is only for the OTHER member of the caller's wedding (`self_target`, other wedding tested), or the reusable pending invitee; the event is written before the admin call; `app_metadata` is merged, the forced-change flag is set and the target's sessions (including a stolen one) are closed (tested).
- Token: 32 random bytes, only sha256 stored (test checks the row never contains the token), 43-char shape check before any call, expiry and single use enforced in the DB (a sign-in makes the account non-reusable), rotation kills the old hash (tested), all bad links give one answer.
- GET is side-effect free (only a lock inside the DB function when the hash exists), dynamic, `no-store`, `no-referrer`, `noindex`. Server actions: zod first, DB-authorised, errors via allowlists (`RPC_MESSAGES`, `KNOWN_DENIALS`, `failureMessage`), codes never logged or returned.
- Link shown once: returned in the action state only, not stored in the DB, not revalidated into the page. Emails off: invite by email refused server-side before any write (`EMAIL_OFF_INVITE`) and hidden in the UI; code path and temp code work (tested).
- Races accept/revoke and accept/email change: deterministic, no 40P01 (tested, DB lock order from code-6).

Open: REV-1 (old link survives a failed rotate), REV-3 (no throttle on the public POST, password changed before the limiter).
Residuals to document (not blocking): a link holder can reset the code until the first sign-in (the link is the credential, 7 days); one partner can lock the other out with a temporary code (D52; mitigated by the event in Novità, the email notice with emails on, and the forced change); a narrow window where an account becomes non-reusable between the DB step and the admin step (same-account, same-credential holder); the token is in the platform request logs (REV-8).

Evaluation of "no usable IP means the gate is open": acceptable. It matches the login limiter's rule (`clientIp` returns null for a missing or malformed address; a shared "unknown" bucket would let one visitor lock out every invitee). The asset behind the gate is a 256-bit token, so an open gate adds no guessing risk; it only loses the cost-amplification brake in the case where there is no IP, which does not happen on Vercel (`x-vercel-forwarded-for` is set by the platform). Residual to record in R27(b) with the existing note: off Vercel the fallback to `x-forwarded-for` is client-controlled, so the gate can be evaded by changing that header.
