# FEAT-2026-001 — code review, round 1 (T6 email layer)

Verdict: changes requested
Scope reviewed: commit 6c7793b (`src/lib/email/**`, templates, `supabase/templates/recovery.html`, `e2e/support/mailbox.ts`, tests). Counts: blocking 0, should 4, nit/could 5.

Verified correct (no action):
- Escaping: every interpolation in the layout, invite, notices, reminders and digest goes through `escapeHtml` (text and quoted attributes, backtick included). Button URLs go through `safeUrl` (http/https allowlist, `URL.href` normalises) and then `escapeHtml`. Palette values come from the static catalogue.
- Header injection: subject, `to`, header names and values and the idempotency key go through `singleLine` (CR, LF, U+2028/9). Both senders use it.
- HMAC: SHA-256 over `context\nkind\nuserId`, so tokens are bound to the kind and the user. `timingSafeEqual` runs only after a length check. Verification allowlists the characters, caps length at 512 and never throws. The URL carries a uuid and no email. No-expiry is acceptable for an unsubscribe link (it only reduces mail, POST is idempotent, and the token is not a login credential). Secret rotation revokes all tokens; document this.
- `emailEnabled`/`NullSender`: `readEmailConfig` never throws, there is no import-time read, and the Null result carries no values (AC59 holds at this layer). Resend uses plain `fetch` with a 10 s timeout, and its error strings are value-free. The API key appears only in the Authorization header.
- The mailbox helper is imported only by e2e (grep: no `src` import) and has no secrets.
- The email-changed notice omitting the new address is right (no PII sent to a possibly-compromised old inbox). The `server-only` alias is the standard Vitest approach. The 5-row cap, "e altri N" and the multi-task subjects follow design and plan §11. Italian copy uses "tu" consistently. `noreply@example.test` fallback is fine (SMTP is local/CI only).
