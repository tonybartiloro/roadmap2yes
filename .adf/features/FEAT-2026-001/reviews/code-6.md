## Security summary

Verified correct:
- RLS enabled on all 8 public and 2 private tables (pgTAP asserts it from the catalog). Every policy goes through `has_permission(wedding_id, area, action)` against `memberships` (DB, not JWT), so revocation is immediate. `family`/`planner` have no rows and read nothing. No INSERT/DELETE/TRUNCATE grants and no table-level UPDATE; column UPDATE grants equal matrix §3.1 exactly (asserted). `id`, `wedding_id`, `created_*`, `slot`, `method` are immutable by trigger and absent from grants; wedding_id moves are refused (42501) and tested via API.
- No dynamic SQL anywhere except the migration-time revoke loop over `regprocedure` (`format('%s')`, catalogue-sourced). All 20+ definer functions set `search_path = pg_catalog, pg_temp`, qualify every relation and cast through `::text`; asserted by pgTAP. Callers are validated (`auth.uid()` null → 42501; membership+permission; `for update` + `has_permission` on rotate/revoke, indistinguishable not-found/forbidden).
- EXECUTE: default privileges revoked, all existing functions revoked from PUBLIC/anon/authenticated, explicit allowlist, asserted both ways (exact list for `authenticated`, none for `anon`, service-only set equals `login_gate`, `login_record`, `auth_user_id_by_email`, `record_heartbeat`; no `private` function executable). `private` schema has no usage for API roles and `api.schemas = ["public"]` (PGRST106 tested).
- `token_hash`: no SELECT on the column (`select *` on invitations is refused on purpose, tested), excluded from audit through `audit_row('token_hash')`, never returned by any RPC; 32-byte check; the old hash is overwritten on rotate and on re-delivery.
- Append-only: `audit_log` and `account_events` have no UPDATE/DELETE grant and row+statement triggers that also block the owner and the secret key (tested including TRUNCATE). The definer insert path writes only INSERTs.
- `create_wedding`: founder from `auth.jwt()->'app_metadata'` (users can only write `user_metadata`); one wedding via advisory lock + `already_member`/`already_created` + unique partial index on `created_by` (double-click test passes with exactly one success); refused with a pending invitation for the account email (BR13).
- Limiter: atomic upsert per key; window restart and lock expiry correct; email and IP keys are 32-byte digests (length-checked), raw values never reach the DB; `login_gate` answer depends only on the keys (no enumeration); success clears the email key only (see REV-5 for the lock edge).
- Invitations: single pending per wedding (partial unique), 7-day expiry, rotate invalidates the old hash, revoke idempotent, `accepted_at`/`revoked_at` exclusive, max 2 partners by `unique(wedding_id, partner_slot)` + role/slot check, so the limit holds even under a race.
- `versionedUpdate`: runs with the user JWT (no service key import), `update ... eq(id).eq(version)`, zero rows → re-read with RLS, so a foreign row is `current:null`; the patch type omits id/version/wedding_id/audit columns; non-conflict errors (42501, 23514) are thrown, not turned into conflicts. Its tests cover the real race and the grant refusal.
- Repo hygiene: no key in tracked files (only placeholders); seeds and test helpers use `@example.test`; `stackEnv()` accepts only `http(s)://127.0.0.1|localhost[:port]` (exact regex, no suffix tricks) before any call, falling back to `db:env` only when env is incomplete; the secret-key client lives in `tests/support`, not in `src`.

Risks left to later tasks (see REV-1/2/3/5): the app-path limiter does not cover direct GoTrue calls (documented R20); `authorize_account_op` is a snapshot, so T7b must order DB mutation before admin call; T7a/T3 must call `login_record` only after an open gate. `config.toml` rate limits (1000) are local only: the remote checklist must set the real per-IP limit.
