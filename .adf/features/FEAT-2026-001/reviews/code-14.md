## Security summary

Checked and OK:
- **Enumeration:** an unknown email, a wrong code and a blocked email give the same texts. A parse failure also gives `INVALID_CREDENTIALS`. The blocked answer comes from the gate before GoTrue, so a blocked email gives the same text whether it exists or not. The recovery request always answers the same. Only residual: REV-5, plus the inherent GoTrue timing outside the app.
- **Limiter order:** gate, sign-in, record, with record only after an open gate (`login.ts:82-116`). A GoTrue 429 counts as blocked and writes no record. An outage is not counted as a wrong code. Only HMAC digests reach the DB, and the tests assert it (`login.test.ts:68`). Real-stack tests cover 5 failures, success-below-threshold and the IP key.
- **Current code on change:** `verifyCurrentCode` uses a throwaway client (no persistence, no cookie writes), through the same limiter, and signs the probe session out. The same-code check before verification is not an oracle. A stale-but-signed JWT cannot change anything because the current code is required.
- **Email change:** typed twice plus the current code, `authorize_account_op` first (event before), admin call on the id and the email the DB returned (not the typed one), `sync_my_email` after, notice to the old address. DB-first per §4.8. `admin-ops.ts` is `server-only` and acts only on DB-returned ids; the `not_partner` branch uses the verified JWT `sub` only. The integration tests prove it never acts on a foreign id.
- **Bootstrap:** only when the typed email matches (normalized), create-only (the exists check is tested, including a code changed in app), founder claim in `app_metadata` (users cannot write it), no values logged (tested), env code validated against the policy, race handled (tested with 3 parallel calls). No `server-only` plus lazy admin import is correct and does not weaken the bundle: `features/auth/bootstrap.ts` is only imported by the server action and the script. Gap: REV-2.
- **P2 settings:** `auth.gotrue-hardening.test.ts` calls `PUT /user` directly. The email change stays pending, the code change with a session older than 24 h is refused, the policy holds for direct calls, and the test states the residual R26 (within 24 h the code can change) honestly. It matches the plan.
- **Session and CSRF:** Next 16 server actions check Origin against Host and `allowedOrigins` is not loosened. The proxy sets `private, no-store` on everything it handles (back button shows no data). The matcher excludes only `_next/static`, `_next/image`, the favicon and image-type assets, never `/api`. Cookies `SameSite=Lax`, but not httpOnly or secure: REV-1.
- **Open redirects:** none. No `next=`/`returnTo` anywhere. Post-login and `/auth/avanti` only pick from fixed paths; the `forced` hidden field only chooses between two DB-derived destinations.
- **Guards:** encoded, dot-segment, backslash and double-slash paths are private (`isPlainPath`). `/api/cron/` is exempt before the outage check and keeps its own Bearer auth. `/email/disattiva` and `/servizio` are public. API without a session gets 401, never a redirect. A member never sees `/accesso` or `/su-invito`. No redirect loop: `none` leads to `/auth/avanti`, which ends on `/su-invito` (public for non-members). The membership query without `user_id` in the guard is correct for an existence check (RLS).
- **Recovery:** `/auth/conferma` renders its form only with emails enabled and `type=recovery`; GET changes nothing; the token is consumed on POST only; `no-referrer` applies under `/auth`; the template links to `{{ .SiteURL }}/auth/conferma?token_hash=...` (not `ConfirmationURL`, so prefetchers cannot burn it). The new code is policy-checked before and after. The fresh session is replaced by a new login with the new code.
- **Secrets:** nothing secret in the client bundle or the repo; `NEXT_PUBLIC_*` only carries the URL and the publishable key. The secret key stays in `server-only` modules (and `bootstrap.ts`, lazily).
- **Accessibility:** labels on all fields, `autocomplete` is `username`/`current-password`/`new-password`, field errors use `aria-invalid` plus `aria-describedby`, feedback is `role=alert`/`status`, buttons have a pending state.

Open: REV-1 (cookies), REV-2 (script target), REV-3 (sign-out on outage), REV-4 (glue tests).
